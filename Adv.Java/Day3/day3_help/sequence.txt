Dis advantages of Cookie based Session Tracking(state management)
1. Can store only text data in a cookie
2. Servlet developer has to manage cookies
3. As no of cookies increase , net trafic increases.
4. Since the state of the user is stored on the client side , if you delete cookies state is lost .
5. If client block the cookies , cookie based session tracking fails


Replace Cookie based State management by HttpSession API


jakarta.servlet.http.HttpSession 
 - interface to represent multiple requests coming from same client from login to logout | session expiration(default for Tomcat=30 minutes)

 
Development Steps
1. Get HttpSession from WC
- Method of HttpServletRequest
 public HttpSession() getSession()
- In case of new user , WC creates a NEW HttpSession object & returns it to caller.
- In case of existing user , WC returns EXISTING HttpSession object to the caller.
Eg . HttpSession session=request.getSession();

1.1 Method of HttpServletRequest
 public HttpSession() getSession(boolean create)
- create : true
 - works extactly as earlier

- create : false
 - In case of existing user , WC returns EXISTING HttpSession object to the caller.
- BUT In case of new user , WC  returns null (does not create any new session)

2. To save client state under HttpSession
HttpSession API
public void setAttribute(String attrName,Object attrValue)
eg . session.setAttribute("user_details",user);

3. To get client details from HttpSession
HttpSession API
public Object getAttribute(String attrName)
Eg . User userDetails=(User)session.getAttribute("user_details");

4. To discard HttpSession (typically in logout page)
HttpSession API
public void invalidate()
- WC marks HttpSession object on the server side for Garbage Collection(GC)

Page Navigation
- Server Pull (Request Dispatching | Request Chaining)
- used commonly in MVC based architecture.
- Navigating the client to next page BUT in the SAME request.
- Dispatching the same request to visit multiple pages (HTML | JSP | Servlet)
Why 
- Division of responsibility(separation of concerns=tasks)
Meaning one web page can be responsible for B.L (business logic) & another page can be responsible for P.L (presentation logic) - response generation logic.
- faster technique than client pull , since doesn't involve round trip delay.

API steps
1. Create Request Dispatcher object, to chain the resources(web pages - HTML , JSP , Servlet)
API of ServletRequest | ServletContext
public RequestDispatcher getRequestDispatcher(String dispatcherLocation)
RequestDispatcher - i/f in the package - jakarta.servlet
Eg. To chain servlet1 -> servlet2
In servlet1 
RequestDispatcher rd=request.getRequestDispatcher("s2");
s2 - url-pattern of the servlet2

2. API of RequestDispatcher
2.1 forward scenario
public void forward(ServletRequest rq,ServletResponse rs);
Eg.
rd.forward(rq,rs);
Internals - 
- WC clears(discards) the resp buffer.
- WC invokes doXXX method of the next page (doGet --> doGet , doPost--> doPost)
- Only the last page in the chain , can generate  the dynamic resp(i.e can add to the resp buffer)
- After the method exec , control comes to the 1st page . 
- resp is then rendered (sent to clnt).
- This is the default technique used for navigation in typical MVC framework.

When will WC throw IllegalStateException?
- If you are calling forward , after committing the response.
OR
- If you are calling sendRedirect , after committing the response.



2.2 include scenario (include method of RequestDispatcher)
public void include(ServletRequest rq,ServletResponse rs);
Eg.
rd.include(rq,rs);
Internals -
- WC does NOT clear the resp buffer(i.e it retains the contents in the resp buffer).
- WC invokes doXXX method of the next page (doGet --> doGet , doPost--> doPost)
- Control comes back to the main page.
- Resp is rendered
- It will contain the dynamic contents from 1st page(main) + include page.
- Included page can't modify resp status code or headers.
(i.e can't use the methods
 - setStatus & setHeader)
- WC simply ignores the changes.



forward vs include
- Both are request dispatching techniques(server pull)
- min scope required : request
Difference
In include scenario
- main page , as well as included page , both , can generate dynamic contents (i.e pw.print)
- The included page can not set resp status code & headers.



Note -
In client pull (i.e clicking on the link/button or sendRedirect)
 - minimum scope required for the attributes : session
Eg. session.setAttribute & session.getAttribute

In server pull (i.e RequestDispatcher - forward | include)
 - minimum scope required for the attributes : request
Eg. request.setAttribute & request.getAttribute
